# Repository Guidelines

## Project Structure & Module Organization
- `src/` contains application code: `components/` shared UI, `pages/` route views, `features/` domain flows, `hooks/` custom logic, `contexts/` providers, `content/` markdown knowledge, `styles/` CSS.
- `public/` exposes static assets; only place favicons, manifest, and raw downloads.
- `dist/` is generated by `npm run build`; do not edit by hand or commit updates.
- `scripts/file-manager/` holds helper scripts for content maintenance; run from repo root when syncing files.
- To add a page, create `src/pages/MyView.jsx`, export default, then register a `<Route>` in `src/App.jsx`.

## Build, Test, and Development Commands
- `npm install` installs dependencies after cloning or updating the lockfile.
- `npm run dev` starts the Vite dev server with hot reload on localhost.
- `npm run build` creates the production bundle; verify no warnings before deployment.
- `npm run preview` serves the built bundle for smoke testing.
- `npm run lint` executes ESLint using `eslint.config.js`; resolve all errors before pushing.

## Coding Style & Naming Conventions
- Write modern React function components and hooks; favour composition over prop drilling.
- Indent with two spaces throughout JS, JSX, and JSON; break JSX props onto new lines past 80 characters.
- Name components and pages in PascalCase (`MainLayout`), hooks in camelCase with a `use` prefix (`useSearchIndex`), and utility modules in lower camelCase.
- Place shared styles in `src/styles/`; prefer kebab-case class names and keep component-specific selectors scoped.
- Run `npm run lint` after significant edits to catch import order and unused symbol issues.

## Testing Guidelines
- Automated tests are not yet wired; rely on `npm run preview` plus manual regression in Chrome and Edge before merging.
- When adding tests, use Vitest + React Testing Library; store specs beside source as `Component.test.jsx`.
- Record manual test notes or edge cases in the pull request description.
- For markdown-driven content, open relevant routes in the preview build to confirm rendering and navigation.

## Commit & Pull Request Guidelines
- Use concise commit titles in English or Chinese, present tense, <=72 characters (e.g., `fix: adjust hero spacing`).
- Keep each commit focused; separate lint-only fixes from feature work.
- Pull requests should include a short summary, linked issue ID, screenshots or recordings for UI changes, and confirmation that lint/build were run.
- Rebase on `main` before opening a PR; resolve any merge conflicts locally.

## Configuration & Secrets
- Duplicate `.env.example` to `.env` for local development; fill in required keys privately.
- Document any new environment variables in both `.env.example` and this guide.
- Never commit secrets, API keys, or the generated `dist/` output.
